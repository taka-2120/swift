# Deferred Macro Resolution

* Proposal: [SE-NNNN](NNNN-deferred-macro-resolution.md)
* Authors: [Yu Takahashi](https://github.com/taka-2120)
* Review Manager: TBD
* Status: **Pitch (prototype implemented)**
* Implementation: [apple/swift branch `deferred-macro-resolution`](https://github.com/swiftlang/swift), gated behind `-enable-experimental-feature DeferredMacroResolution`

## Introduction

This proposal adds an explicit, opt-in relaxation of the "simultaneous
expansion" model introduced by [SE-0389 (Attached Macros)](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0389-attached-macros.md):

```swift
@freestanding(declaration, resolution: deferred)
public macro Preview(...) = #externalMacro(...)
```

A freestanding macro that declares `resolution: deferred` allows name lookup
within its *arguments* to trigger — and observe — the expansion of attached
macros, instead of pretending all macros in scope expand simultaneously. The
opt-in is restricted to macros that introduce no names of their own, which is
what keeps it free of expansion cycles.

## Motivation

SE-0389 states that each macro expansion operates independently, and that a
name introduced by one macro expansion is not visible within the arguments of
macros in the same or enclosing scopes. This principle keeps expansion
order-independent and compile times predictable.

However, it also produces one of the most commonly reported macro pitfalls:
**`#Preview` cannot see members generated by `@Observable`** (or by any other
attached macro) when the annotated type lives in another file:

```swift
// Model.swift
@Observable final class Model { var value = 0 }

// ContentView.swift
#Preview {
    let model = Model()
    let _ = model.access(keyPath: \.value) // error: value of type 'Model'
                                           // has no member 'access'
    ContentView(model: model)
}
```

Apple engineers have confirmed there is no workaround. Both features behave
as designed; the *combination* is what fails. Yet the strictness is wasted
here: `#Preview` is a development-only macro whose expansion introduces no
names that other code could ever reference, so nothing about its own
expansion can feed back into the type checker.

Empirically (verified against the current compiler), the restriction bites
whenever a *declaration-position* freestanding macro's argument references
macro-generated declarations from a library file — the normal state of every
file in a real project — regardless of whether the attached macro's type is
declared in the same file. (Main-file top-level code and expression-macro
arguments inside function bodies are not subject to the check, which is why
single-file reproductions misleadingly appear to work.)

## Proposed solution

Add an optional `resolution:` argument to the `@freestanding` attribute with
two values:

* `independent` (the default; current SE-0389 behavior)
* `deferred` — name lookup inside this macro's arguments may expand and see
  attached macros in the same scope

```swift
@freestanding(declaration, resolution: deferred)
public macro Preview(
    _ name: String? = nil,
    @ViewBuilder body: @escaping @MainActor () -> any View
) = #externalMacro(module: "PreviewsMacros", type: "SwiftUIView")
```

`resolution: deferred` is only permitted on freestanding macros that
introduce no externally visible names:

* `@freestanding(expression)` macros — always allowed, and
* `@freestanding(declaration)` macros **without a `names:` list** (they may
  still create declarations under compiler-generated unique names, as
  `#Preview` does).

Any other role, or a declaration macro with `names:`, is rejected:

```swift
@freestanding(declaration, names: named(A), resolution: deferred)
// error: 'resolution: deferred' can only be used with freestanding macros
// that do not introduce names
```

## Detailed design

### Why this cannot introduce expansion cycles

The independence rule exists because resolving a name inside a macro argument
may require expanding a macro whose own expansion requires type-checking that
very argument — a cycle. The cycle needs two ingredients: (1) lookup inside a
macro argument triggering expansions, and (2) the *deferred macro itself*
being one of the macros lookup may need to expand.

Restricting deferral to macros that introduce no names removes ingredient
(2): name lookup never has a reason to expand the deferred macro, because no
lookup result can originate from it. Dependencies therefore flow one way —
from the deferred macro's argument to other macros' outputs — and terminate.
Should an unexpected cycle arise through other means, the request evaluator's
existing cycle detection still diagnoses it rather than hanging.

### Semantics

When type-checking a source location, the compiler decides whether it is
"inside a macro argument" to determine whether name lookup may consult macro
expansions (`ExcludeMacroExpansions`). With this proposal, a freestanding
macro expansion whose name resolves *only* to macros declared
`resolution: deferred` no longer marks its argument range as excluded; the
walk continues outward, so an enclosing independent macro argument still
re-imposes exclusion. If the macro reference is ambiguous and any candidate
is independent, the conservative (independent) behavior wins.

The macro's own expansion timing is unchanged: arguments are still fully
type-checked before the macro expands. Deferral only widens what those
argument type checks can see.

### Serialization and module interfaces

The `resolution:` argument is serialized in the macro's module and printed in
`.swiftinterface` files (omitted when `independent`), so a deferred macro
declared in a library — the `#Preview` scenario — behaves identically when
imported.

## Source compatibility

Purely additive. Existing macros are unaffected; code that previously failed
to compile inside deferred macros' arguments now compiles, which is
source-compatible in the forgiving direction.

## ABI compatibility

None. Macros are compile-time only.

## Alternatives considered

* **Opting in on the attached-macro side** (e.g.
  `@attached(member, visibility: eager)` on `@Observable`, meaning "my
  expansions may be observed from other macros' arguments"). This looks
  symmetric but has strictly weaker properties. First, the acyclicity
  argument evaporates: attached macros introduce names by definition, so two
  eager producers whose expansions reference each other's output reconstruct
  a genuine expansion cycle — the property degrades from "structurally
  impossible" to "detected at run time with a cycle diagnostic". Second, the
  independence guarantee being waived belongs to the macro that owns the
  arguments; a producer-side flag silently changes how *other* macros'
  arguments type-check (`#Predicate`, `#expect`, …), yielding
  action-at-a-distance and mixed visibility within a single argument (members
  from eager macros resolve, others do not). Third, deployment scales
  poorly: every producer in the ecosystem must adopt and individually reason
  about cycle risk it cannot verify locally, and eager `arbitrary`-named
  macros would re-create the global-scope lookup cost that motivated
  SE-0389's top-level `arbitrary` ban. A consumer-side opt-in is one
  declaration on a small, identifiable set of capture-style macros, and
  immediately covers all attached macros, including third-party ones.
* **Fixing `#Preview` specially in the compiler.** Solves one symptom;
  third-party development-time macros (snapshot testing, fixtures, DSL
  previews) hit the same wall.
* **Globally relaxing SE-0389 for attached-macro members.** Changes the
  meaning of existing code, reopens the cycle analysis for every macro, and
  contradicts the accepted design. An explicit opt-in keeps the default
  guarantees intact and the review surface small.
* **Spelling it as a separate role or attribute** (e.g.
  `@freestanding(deferredExpression)`). The behavior is orthogonal to the
  role, and an argument leaves room for future values.

## Future directions

* Allowing `resolution: deferred` on declaration macros *with* names, backed
  by a proper dependency analysis between introduced names and argument
  lookups.
* Adopting `resolution: deferred` in SwiftUI's `#Preview` and similar
  development-only macros.
